# Data, consent and abuse boundary

## Non-negotiable handling

| Data | V1 treatment | Retention/control |
|---|---|---|
| Current location for lookup | Permission only when “from here” or active journey chosen; transient POST to Mira; provider transfers disclosed. | Browser memory outside trip; no passive history. |
| Chosen live journey | Only after explicit start; per-contact share action, last-position age visible. | Preserve current max 20 active points, delete at close, purge journey per existing 6h contract unless a reviewed change is approved. |
| Future intent/planned trip | Sensitive origin, destination, time and purpose. Default ephemeral, no automatic account history. | Save only by user action; deletion and expiry shown. Avoid analytics copies. |
| Saved places/contacts | Existing encrypted account storage; contacts accept/receive separately. | User can remove; recipient link revocable and expires. |
| Chat | Current API stores user text verbatim up to 30 days and scrubs assistant location fragments. V1 must not turn it into a location diary. | Clear history; introduce stronger minimisation/ephemeral planning mode before broad intent storage. |
| Community fact | Separate raw observation from eligible derived claim; no contributor/public identity. | Source-specific expiry, withdrawal and moderation audit. |
| Incident narrative | Keep current encrypted/coarse/private intake and ≤30-day purge as floor. | Never auto-publish exact place/time/person. |
| Product metrics | Coarse events: plan started, useful option produced, action confirmed, provider failure, correction, journey completed. | No coordinates, precise routes, message text, names or contact links; aggregate/retention policy before shipping. |

Existing controls include same-origin checks, rate limits, CSP, encrypted contact/place/report fields, per-contact bearer links, worker retention and operational audits. Maintain regression tests. Server-to-provider geocoding may include **rounded** coordinates in a GET URL even though browser-to-Mira requests use POST bodies. Do not claim otherwise. [Current location boundary](../LOCATION_PRIVACY.md), [current retention](../../src/server/retention.ts), [report policy](../../MODERATION_POLICY.md).

**Phase 1 implementation:** The plan draft lives in versioned `sessionStorage` for one tab, with a two-hour expiry after the last edit and a Clear plan action; storage failure falls back to memory. It is not attached to account history, server plan storage, analytics or `/api/mira`. Named-place search sends the typed query to the public `/api/geo/search` endpoint; the request has no device coordinates for a remote plan. Search/provider handling may still have its own operational logs and third-party query transfer, so the draft's local retention must not be mistaken for a guarantee about geocoder query retention. The selected plan location source is recorded as search, saved place, selected point or explicit `from_here` device point. Opening Around or map with an active named-origin plan suppresses legacy automatic location requests.

**Phase 2 provider-rights audit:** [Google Routes policy](https://developers.google.com/maps/documentation/routes/policies) requires Google route content shown on a map to use a Google Map. [Google Places policy](https://developers.google.com/maps/documentation/places/web-service/policies) restricts storage of Places content. Planned-place searches use the local OSM snapshot and configured Photon source, excluding Google and the public Nominatim deep lookup. The new planned-option endpoint uses only MIRA's imported OSM graph and returns no Google route content. As a defensive boundary for any Google result selected through another path, `sessionStorage` keeps the person's typed query but drops the provider name and coordinates; reload asks for a fresh selection. The new endpoint has no plan or route-trace database write. Existing live-map/provider paths are a separate rights audit item before their expansion, especially when Google tiles fall back to another map provider. Public OSM/Photon endpoint quotas and attribution need an operations review before larger traffic.

**Phase 3 local Ask review:** A plan question uses `/api/mira/plan`, not the legacy 30-day `mira_messages` POST. Both guests and signed-in plan users receive a deterministic, no-model NDJSON reply from checked evidence. The endpoint writes only existing rate-limit counters (20/minute, 100/day by IP for ordinary questions), and neither logs nor stores question text or route traces. Urgent messages emit the Emergency card before database/model work. A new text intent becomes only a two-hour tab draft with unresolved places and blank planned time/zone, so no remote time is guessed. [Detailed review and release-open items](25_PHASE_3_PRIVACY_REVIEW.md).

**Phase 4 local journey review:** `startTripSchema.share` now defaults false for direct clients, Home selects “Just me” by default, and legacy Ask starts a private trip. The separate plan-start confirmation states the selected Circle recipients, if any, before requesting a fresh position. The server retains the existing maximum 20 points, four-hour journey cap, contact tokens, close deletion and six-hour purge. The active browser watch stops while hidden. A confirmed change updates destination/ETA on the same owner-checked journey and token; it does not add recipients or send contact mail. The provider route refresh uses the local OSM graph and stores selected geometry only on the device. Real-device behavior and independent privacy review remain open release evidence.

**Phase 0–7 audit finding:** An unmapped walking loop now offers an explicit manual check-in interval through the existing no-destination trip path. The button alone makes no location request; after a separate confirmation the client requests a fresh device fix and checks proximity to the named origin before sending `from`, the chosen interval and `share` (false by default). It sends no route or destination to the trip API, does not claim automatic return detection, and leaves denied-location plans intact. Account sign-in is still required for a live trip; guest planning remains available without it. Promoting a complete named return leg changes only the tab draft and does not save, start or share.

**Phase 5 remote-plan review:** Added legs and destination country choices use the same two-hour `sessionStorage` draft, with no plan database write, account save, contact exposure or itinerary analytics. New legs leave time and zone blank until entered. OSM/Photon search receives the typed name without device coordinates; the selected public country profile endpoint receives only an ISO code. Google result name/point content is stripped from every leg before session persistence. Plan Ask still uses the ephemeral rate-limited route without raw text history; its urgent path bypasses the database first. A chosen destination country is labelled as future planning context and never changes the current-location Emergency dial action. Browser search and country fixtures do not prove live provider rights, reachability or quota behaviour; those remain operations review items.

**Phase 7 explicit save and habit transition:** The default plan remains a two-hour tab draft. A signed-in person can choose Save plan for a valid named-origin plan; current GPS origins, Google result content and incomplete added legs are refused. `/api/me/plans` stores the draft as AES-GCM text with a separate `saved_plan` purpose, only under its owner, for at most 30 days. Up to ten plans may be saved; Journeys shows expiry, opens an editable copy and deletes by owner action. The retention worker purges expired rows and account deletion cascades. No save/share/start follows merely from opening a plan. Migration `0020` preserves the old habit setting in `legacy_remember_habits`, sets learning and suggestions off for all existing accounts, changes the new-account default to off, and records an explicit future choice. Old habit summaries remain visible for review/deletion until their existing 400-day retention; switching off deletes them. Local integration tests verify owner scoping, encrypted payload, expiry/deletion and no habit use before choice. Independent privacy/security review and staging migration rehearsal are still required.

## Consent and adversarial checks

No default sharing, background tracking or inference-based alerts. Ask permission at use; show recipients, action/delivery state, and a revoke control. If the account or phone is compromised, a person must be able to end sessions and trip links and delete saved plans. Notifications must not reveal destinations on lock screens. A contributor can skip, use private or aggregate-only paths where available, and withdraw a claim through a documented channel. New community classes need malicious-correction, brigading, false accusation, insider and data-broker threat reviews.

**Historical default and current gate:** migration `0012` originally set `remember_habits=true`; forward migration `0020` pauses collection/use and keeps the old setting for review. The code and test gate passes locally, while a privacy owner must still approve the migration notice, old-row retention choice and staging rehearsal before release. [Migration details](19_MIGRATION_PLAN.md).

No provider/LLM data use is implied by an in-app privacy toggle; validate actual contracts and data flows. Third-party Places content is subject to storage/display restrictions. [Google Places policies](https://developers.google.com/maps/documentation/places/web-service/policies).
