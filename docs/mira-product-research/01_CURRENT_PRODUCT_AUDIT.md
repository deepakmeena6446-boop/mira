# 01 — Current product audit

**Audit basis (2 October 2026).** I read the current screens, API handlers, domain rules, migrations, provider adapters, privacy copy and existing tests. I also ran the local app at `localhost:3100` and inspected the signed-out first-open, Today, Around, Mira, Contribute and map screens. The local page served successfully. I did not grant browser location or create an account, so signed-in and location-aware journeys below are verified from implementation and tests, not a live end-to-end user session. Existing product specs are treated as intent, not proof of delivery.

## What a new user experiences

The first-open message is **“Know more. Move freely. Together.”** It describes three actions: know a place, move with support and help the next person. Location is optional. The stable navigation is **Today / Around / Mira / Contribute / You** ([welcome](../../src/app/welcome/Welcome.tsx#L50), [tab bar](../../src/components/app/TabBar.tsx#L10)). Today first offers **Check a place**, then **I feel unsafe / Emergency**, then Ask Mira, Local pulse, journey and contribution links, Circle and city-level updates ([Today](<../../src/app/(app)/TodayScreen.tsx#L43>)). Around is a place search and brief; the full map and route planning live one level deeper ([Around](<../../src/app/(app)/around/AroundScreen.tsx#L51>), [map page](<../../src/app/(app)/around/map/page.tsx#L12>)). A signed-out user can search and report, but cannot converse with Mira or start a followed journey ([Mira chat](<../../src/app/(app)/mira/MiraChat.tsx#L197>)).

**Accidental architecture:** this currently feels like a **safety companion feature hub with a place/map core**. It is not simply map-first after the latest navigation change, but the strongest concrete task is still checking a place or setting up a journey. Ask Mira is visible as a peer tab yet often serves as a natural-language launcher for map, Help Point, report and trip cards. “Local pulse,” reports, news updates, lighting and Help Points are parallel evidence surfaces rather than one coherent answer to “I want to do this; how should I do it more safely?” The many separate “safety” entrances impose interpretation work on the user.

## Data and trust architecture in practice

- **No area safety score is implemented.** The code exposes route lighting percentages, source/evidence states and rules-based Help Point ordering, not an “8/10 safe” index ([context claims](../../src/domain/context.ts#L4), [privacy copy](<../../src/app/(app)/privacy/page.tsx#L162>)). This restraint should survive.
- **The core local evidence is fragmented.** Route API joins walking geometry, lighting, Help Points and thresholded notes; it does not synthesize a recommendation or explain which option better fits a particular intent/time. Ask Mira can access a subset through tools, but it does not get the route alternatives or a general contextual inference engine ([route API](../../src/app/api/geo/route/route.ts#L58), [Mira tools](../../src/server/providers/companion/tools.ts#L25)).
- **Reports are carefully protected but usually cannot improve a user's current decision.** Raw reports need human moderation, then five independent submissions in the same area/time/category, then a Monday release, with publishing disabled unless explicitly turned on. This is appropriate as a cautious beta posture; it is not yet a strong community data advantage ([moderation](../../src/server/admin/reports.ts#L101), [aggregation](../../src/domain/aggregation.ts#L1), [release job](../../src/server/aggregate/run.ts#L17)).
- **Place checks are a distinct and potentially faster evidence loop.** Two corroborating independent place corrections affect Help Point filtering; three agreeing walkers affect lighting. This loop is still narrow and density-dependent ([help server](../../src/server/help-points/index.ts#L189), [lighting](../../src/domain/lighting.ts#L21)).
- **Provider quality is variable.** Google is the configured real maps adapter when a key is present; otherwise local OSM plus external OSM services and approximate routes take over. A successful UI lookup should never be read as complete coverage. Source failure is represented separately from “none found” in APIs ([provider modes](../../src/server/providers/modes.ts#L8), [geo factory](../../src/server/providers/geo/index.ts#L8), [evidence state](../../src/domain/evidence-state.ts)).
- **Operational dependence is real.** Email and push need credentials; missed-check-in monitoring needs the worker; live location needs the foreground trip screen. These are materially different from a native always-on safety service ([trip screen](<../../src/app/(app)/trip/TripScreen.tsx#L198>), [worker](../../src/server/journey/worker.ts)).

## Location, privacy and instrumentation

Current location is held in browser memory, with location permission offered rather than required at welcome. Coordinates go in POST bodies for app API lookups; some external geocoding interfaces still use rounded coordinates in provider URLs ([location store](../../src/lib/location-store.ts#L6), [location privacy](../LOCATION_PRIVACY.md)). Reports keep a coarse cell and encrypted narrative; journey traces are short-lived, while chat user messages are stored exactly as typed for up to 30 days even though assistant location-derived details are scrubbed ([report submit](../../src/server/report/submit.ts#L40), [retention](../../src/server/retention.ts#L16), [Mira API](../../src/app/api/mira/route.ts#L48), [privacy](<../../src/app/(app)/privacy/page.tsx#L109>)). Saved places/contacts are encrypted. Habits store destination identity, mode, approximate start hour and counts, not paths; daily action-kind adaptation remains on device ([habits](../../src/server/account/habits.ts#L6), [usage signal](../../src/lib/usage-signal.ts#L1)).

There is **no product analytics tracker or structured funnel instrumentation** in the app. `src/instrumentation.ts` validates startup configuration. `usage-signal.ts` is local personalisation, not a server analytics stream. Server logs and audit records cover operations, moderation and failures, but cannot answer first-use, repeat-use, query-success, help-point-action or journey-completion questions at a product level. That leaves core value assumptions largely unmeasured ([instrumentation](../../src/instrumentation.ts), [usage signal](../../src/lib/usage-signal.ts), [privacy copy](<../../src/app/(app)/privacy/page.tsx#L162>)).

## Direct implications for the founder thesis

1. **The runner feedback is consistent with the implementation.** Mira has facts about mapped light and nearby Help Point types, but no reliable 4:30 AM route/activity picture, scenario-specific option comparison or uncertainty-aware decision guidance. The current AI contract explicitly declines any safety judgment and is likely to route her to Help Points. That is a product-capability gap, not a copy bug.
2. **The strongest assets worth carrying forward are the evidence discipline, working place/route plumbing, explicit failure states, Help Point hours logic, privacy controls, live journey support and structured contribution pipeline.** They form a foundation, not yet a complete answer.
3. **The weakest current claim is “local intelligence” in sparse geographies.** Public community releases are off, lighting and checks require density, city news lacks route specificity, and provider fallback can be approximate. Any redesign must expose coverage and missing data honestly.
4. **The product currently asks users to assemble context themselves.** Today, Around, Mira, map, news, Local pulse and Help Points all describe parts of the world. The primary job should be tested as a situation-to-options flow before deciding which of these deserves first-level navigation.

## Audit limits and verification next

I inspected a running **signed-out, location-denied** local build and code paths; I did not submit a report, use production credentials, grant real location or create a trip. The next research phase should observe signed-in women completing concrete tasks (the early-morning run, unfamiliar late arrival, post-event journey, immediate discomfort), and review real environment coverage metrics before treating any data source as globally dependable. No production files or database state were changed for this audit.
